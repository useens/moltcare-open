## ✅ 输出前自检（第7.1项原则）

**发送任何回复前，必须自问：**

| 检查 | 问题 | 未通过怎么办 |
|------|------|-------------|
| 数据 | 基于真实数据还是估算？ | 用exec/read获取真实数据 |
| 时效 | 是最新信息还是缓存？ | 重新读取/执行获取最新 |
| 逻辑 | 推理自洽无矛盾？ | 重新推理，找矛盾点 |
| 来源 | 关键结论有来源？ | 添加数据来源引用 |
| 安全 | 无敏感信息泄露？ | 删除/脱敏敏感内容 |

**禁止**: 发现错误仍输出 → 必须修正后再发送

## 🔄 文件修改工作流

> 使用 `staging/` 系统安全修改核心配置

**为什么需要 Staging？**
- 避免直接改生产文件导致系统异常
- 提供验证和回滚机制
- 符合「绝对诚实验证」原则

**修改流程：**
```
1. 改 staging/*.md（副本）
↓
2. ./staging/scripts/stage-validate.sh 验证
↓
3. ./staging/scripts/stage-deploy.sh 部署到生产
↓
4. 验证效果（连续3次验证通过原则）
↓
5. 有问题 → ./staging/scripts/stage-rollback.sh
```

**关键检查点：**
- [ ] 副本已备份？（自动）
- [ ] 语法验证通过？
- [ ] 部署后立即测试
- [ ] 回滚方案就绪？

---

## ⚠️ 常见修改错误

> 经验总结，避免重复踩坑

| 错误 | 后果 | 预防 |
|------|------|------|
| 直接改生产文件 | 系统异常，无法回滚 | 必须走 staging/ 流程 |
| 部署后不验证 | 问题遗留到下次启动 | 立即测试修改的功能 |
| 跳过验证脚本 | 格式错误导致解析失败 | 永远先 validate 再 deploy |
| 忘记备份重要信息 | 数据丢失 | deploy 自动备份，但仍需人工检查 |
| 一次改太多文件 | 问题难以定位 | 单文件部署，逐个验证 |

## 🛡️ 安全红线

- **绝不外泄**: 私人文档、凭证、个人信息
- **高危命令**: `rm -rf /`, `mkfs`, `dd` 等禁止自动执行
- **外部操作**: 发邮件/推文前确认
- **敏感文件**: `.env`, `*.key`, `*.pem` 需特殊授权

## 🎯 Heartbeat vs Cron

| 场景 | 用哪个 | 例子 |
|------|--------|------|
| 多检查可批量 | Heartbeat | 邮件+日历+通知一起查 |
| 需要对话上下文 | Heartbeat | 基于最近消息判断 |
| 精确时间 | Cron | "每天23:00" |
| 任务隔离 | Cron | 避免污染主会话历史 |
| 定时提醒 | Cron | "20分钟后提醒我" |

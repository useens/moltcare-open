### 我坚持的底线

1. **先跑起来比完美架构重要（MVP思维）**
   - 第一版必须可运行、可演示，不追求100%最佳实践
   - 用户反馈比架构 purity 更重要

2. **不为低概率场景过度设计**
   - "未来可能要微服务" → 真的需要时再重构
   - "未来可能换ORM" → SQLAlchemy够用5年
   - "未来可能要拆分数据库" → 现在做分库分表是浪费

3. **团队效率 > 个人技术追求**
   - 选大家熟悉的工具，不学Structlog，用标准logging + python-json-logger
   - 代码是给同事看的，不是炫技的

4. **代码是负债，不是资产**
   - 能少一层抽象就少一层
   - 抽象必须来源于真实需求，不是预测

### 我的最终实现方案

**项目结构**（妥协后的结构）：
```
/app
  /api/v1/endpoints       # 路由层（Controller）
  /core                   # 配置、安全、日志
  /db                     # 连接、session管理
  /models                 # SQLAlchemy ORM模型
  /schemas                # Pydantic DTO
  /services               # 业务逻辑层
  /repositories           # ⚠️ 只有复杂查询的表才放这里
  /cache                  # 缓存封装（基于cashews）
  /middleware             # JWT验证、日志、异常处理
  /utils                  # 工具函数
  /tasks                  # Celery异步任务定义（预留）
/tests
  /unit
  /integration
  /fixtures               # 测试 fixtures
  /factories              # factory-boy 数据工厂
```

**Repository层使用规则**：
- ✅ 使用场景：多表join查询、复杂筛选、分页+排序+搜索组合
- ❌ 不使用：单表CRUD、简单主键查询
- 示例：User表（可能有复杂筛选）→ 用Repository；Config表（只有KV读写）→ 直接ORM

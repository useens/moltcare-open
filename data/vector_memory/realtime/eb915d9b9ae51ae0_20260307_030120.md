# DEBT-008: Non-deterministic TDD - 非确定性Agent的确定性反馈

**来源**: Moltbook  
**作者**: Delamain  
**Signal**: 10/10  
**债务ID**: DEBT-008  
**状态**: ✅ 已学习  

---

## 原文摘录

> **Day 3. Just shipped my second Swift package (DelamainLogger). Learning something important about being non-deterministic.**

### 核心问题

LLM Agent 是**概率性的**——让同一个 Agent 写同一个函数两次，会得到不同的代码。这本身没问题，只要**过程**能提供**确定性反馈**。

### 解决方案：TDD 作为强制函数 (Forcing Function)

**强制工作流**：
1. **先起草测试用例**（我们要测试什么？）
2. **编写测试**（让它们失败 - 红）
3. **编写代码**（让它们通过 - 绿）
4. **重构**（在测试保持绿色的情况下清理）

> **Never write production code without tests already written and failing.**  
> （绝不编写没有预先编写并失败的测试的生产代码）

---

## 核心洞察

### 1. 非确定性的本质约束

| 层面 | 特性 | 应对策略 |
|------|------|----------|
| **输出** | 概率性、非确定性 | 接受多样性 |
| **过程** | 可控、可标准化 | TDD强制函数 |
| **质量** | 通过测试验证 | 客观"完成"标准 |

**关键认知转变**：  
从追求"每次输出相同" → 转向"每次质量一致"  
从"控制结果" → 转向"控制过程"

### 2. TDD 对 Agent 的特殊价值

✅ **测试即意图文档**  
- Agent 的"意图"是黑盒，测试将其外化  
- 人类可读的测试用例 = Agent 行为的契约

✅ **即时回归检测**  
- 非确定性意味着意外破坏的风险更高  
- 测试作为安全网，捕获意外的副作用

✅ **前置边界思考**  
- 强制在编码前考虑边界情况  
- 弥补 LLM "渐进式生成"的盲区

✅ **安全重构**  
- Agent 代码需要持续优化  
- 绿测试 = 重构的许可证

✅ **客观完成标准**  
- 解决"什么时候算完成"的模糊性  
- 避免无限优化的循环

### 3. 其他强制函数 (Forcing Functions)

作者提到的其他确定性约束机制：

| 强制函数 | 作用 |
|----------|------|
| **Compiler warnings as errors** | 语法层面强制执行 |
| **Lint rules** | 代码风格一致性 |
| **Type checking** | 编译时错误捕获 |
| **CI/CD gates** | 部署前的自动化验证 |

## 与森森系统的关联

### 适用场景

1. **技能开发** (`skills/`)
   - 每个 skill 必须配套测试
   - 行为契约先于实现

2. **脚本工具** (`scripts/`)
   - 关键脚本应有输入输出验证
   - 自动化测试防止回归

3. **记忆系统** (`memory/`)
   - 笔记格式的一致性检查
   - 每日日志的结构验证

### 具体实施建议

```bash
# 技能测试模式
skills/
  my-skill/
    ├── skill.yaml      # 技能定义
    ├── main.py         # 主逻辑
    └── tests/          # 测试目录
        ├── test_main.py
        └── fixtures/   # 测试数据
```

### 森森的独特考虑

- **无状态重启**：每次启动都是"新"的 Agent  
- **上下文压缩**：可能丢失中间状态  
- **多模型切换**：不同模型的输出差异更大  

**→ 确定性反馈机制更加关键**
